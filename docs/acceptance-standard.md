# 用例生成与验收规范

按步骤查看接口校验、设计门禁、执行分流、runner 限制、模型超时、证据与中断恢复：[测试执行全流程与约束](test-execution-process.md)。

## 适用范围

本规范是平台默认验收标准，适用于新生成、修正或继续执行的验收用例。用户可勾选已有用例作为自定义必验集合，完成只读范围设计核对且 readiness 为 ready 后进入执行准备；ready 表示“设计审查完成”，不代表环境可执行，自定义结论不代表默认全量验收通过。设计审查与执行准备分开。规则与界面操作见 [测试策略规则](test-policy.md)。基线提取、生成、覆盖及评审仍属于 SELF_TEST，不增加顶层阶段；界面区分“正在生成用例”“正在审查用例”和“正在核对自定义范围”。

## 需求验收基线

- 从 PRD、设计图和用户目标提取 REQ-001 格式的需求 ID、feature 功能点名称、明确出处、可观察验收条件、默认是否必验及适用场景。旧基线无功能点名称时按需求 ID 和验收条件分组，不强制重提取。
- 用户明确要求必须为必验。不得从当前实现反推正确答案，不得擅自豁免要求；存在歧义时询问用户。
- `required=false` 仅用于明确标注为建议的补充验证；性能、安全、执行成本高或缺少环境都不是豁免明确要求的理由。分类、优先级、执行与阻断策略详见 [测试策略规则](test-policy.md)。
- 适用场景为 normal（正常）、boundary（边界）、negative（异常）、permission（权限）、state（状态及持久化）。按风险选择，不要求无意义的全组合。
- 基线在本轮验收中保持不变；恢复业务编码后重新提取。当前由模型提取，不等同于人工签署的需求基线。

## 用例质量门禁

- 按验收基线的必验需求及适用场景优先计算待覆盖项，分批生成；之后在独立预算内生成补充用例。单条用例可关联多个需求，但只使用一个场景类型。数量服从验证需要，不凑数。
- `SELF_TEST_BATCH_SIZE` 默认 8，范围 1 至 20；`SELF_TEST_MAX_CASES` 默认 300，范围 1 至 1000。达到总上限仍有缺项时明确拒绝，不截断需求。配置非法时停止规划而非静默采用默认值。
- 上条的强制缺项指必验需求。`SELF_TEST_OPTIONAL_MAX_CASES` 默认 16，范围 0 至 1000，限制仅关联非必验需求的补充用例数；设为 0 不追加补充用例，不删除已保存清单。补充生成同时受总上限约束，预算耗尽只记录非必验覆盖缺项，不阻断必验覆盖；预算不是执行超时或负载限制。
- 每批字段、文件独立性与指定场景覆盖通过后立即保存，追加连续且唯一的 TC 编号。批次无效最多局部尝试 3 次；中断保留已有有效批次，继续时补齐缺项，不重写已通过证据。
- 默认模式全量清单先统一检查结构及必验场景覆盖，再按批进行语义质量评审；任何一批拒绝或评审未完成均禁止默认执行。生成、评审、通过和拒绝状态随任务持久化，用于区分中断续接与质量反馈修正。

- 每条用例必须提供需求 ID 映射、场景、前置条件、测试数据、操作步骤、明确预期、可观察断言与清理方式；不需要数据或清理也要说明原因。
- `preconditions`、`testData`、`cleanup` 的规范生成格式均为非空字符串，每个不超过 2000 字符，不生成数组或对象；多项内容使用字符串内换行，JSON 中换行须转义为 `\n`。兼容解析仅将非空纯字符串数组按换行连接，并将非空 `testData` 对象通过 `JSON.stringify` 转为字符串；已有字符串保留原文，不截断，超长值及显式的 null、空数组、空对象或混合类型数组拒绝。修正时省略字段保留旧值，已通过用例不改写。兼容归一化只处理格式，不代表结构或语义质量门禁通过，仍须验证可复现性、数据充分性及清理合理性。
- 新用例还需提供分类、标签、优先级、风险理由与执行建议。缺少分类的旧用例继续全部必验，定点修复不会自动降级。阻断策略由平台根据需求映射计算，不采信模型自行声明的非阻断标记。
- 全部必验需求的每个适用场景均须有结构完整的用例；未知需求引用、缺失字段及重复测试文件不可通过。
- 预期来自需求约定；断言验证真实业务结果及需求要求的持久化、副作用，而非仅检查成功提示、元素存在、mock、恒真值或命令退出。
- 模型只读评审需求与用户决策、基线完整性、场景充分性及用例定义中的前置条件、数据、步骤、预期、断言和清理是否可判定。设计依据不足则拒绝；评审输出必须为可校验 JSON。设计审查不读取测试文件来核对脚本与断言一致性，不因文件、URL、runner 或实际环境缺失而拒绝设计。
- 默认结构或质量评审拒绝时保留 issues 与 caseIssues，转 REVIEW，阻止默认执行。明确修正操作只修复问题关联 ID，不因任一问题重写全部未执行项；旧问题兼容提取明确 TC 编号。没有编号的全局问题重新评审，不扩展全量修复。用户也可确认自定义集合，单独评审选中项。旧任务没有验收结果时不得默认为通过。
- 人工项可以通过设计质量门禁，但其执行状态仍为 manual，不能作为执行通过。

生成用例与用例执行是纵向独立模块，不提供标签切换：生成模块始终保留设计审查、范围选择与用例定义；执行模块展示已保存计划的选中清单，修改待提交范围不改变已有执行记录。逐条评审只读取显式 `caseReviews`：unreviewed、reviewing、qualified、warning、rejected、unknown。旧记录缺失时为 unknown，不从聚合 qualified/rejected、问题未提及该编号或运行 passed 推断单条合格；自定义范围核对独立展示，不覆盖默认评审。

## 执行与成功标准

- 设计门禁通过不等于环境可执行或开发成功；执行前保存本次计划的时间、每条用例是否选中、阻断策略与判定理由。只执行选中项，执行准备、运行结果与证据独立保存。
- 默认模式至少一条阻断用例、全部阻断用例 passed、工程检查全部通过、默认用例验收 qualified，才能产生新的 SUCCESS。默认模式仅有补充用例不能产生成功结论。
- 补充项失败或未验证不阻断 SUCCESS，但必须保留警告与证据，不计为通过。按需未选中与执行失败分开展示；不把未选中项改写成 skipped 或 passed。
- 执行准备产生的 manual、skipped 不更改设计审查结果，不算执行通过。阻断项的 manual、skipped、环境阻塞、执行失败均阻止 SUCCESS；接受风险为 ACCEPTED，不清除证据，也不等价于 SUCCESS。
- 用户可以在执行结果区选择尚未执行的按需补充项，通过自测接口的 selectedCaseIds 显式执行。该选择只增加本次执行范围，不改变阻断策略，不取消必验项；选择未知、重复或已执行的 ID 会被拒绝。
- 用例修正后必须重新经过门禁；沿用已通过用例时仍须检查整份清单。测试文件优先于浏览器，本机应用需事先启动。测试文件、URL、runner 和实际环境条件由执行阶段检查或在运行中暴露，已有测试文件不要求属于本次 Git 变更。
- 自定义模式覆盖本次阻断范围：至少一条有效的已有用例，填写理由并确认，完整只读设计核对后 `executionAssessment.readiness=ready` 才可进入执行准备；仍须全部选中项有实际 passed 证据、工程检查通过，方可产生范围限定的 SUCCESS。符合版本条件的已有通过证据可沿用。默认评审、未选中结果与范围警告保留，不修改基线，不把未选中项记为通过，不宣称全量验收。
- 自定义质量 `status` 与设计审查 `readiness` 独立：覆盖缺口、映射或分类不完整、较弱断言属于 coverage / quality 警告，允许 rejected + ready；较弱断言仍须有可观察、可判定的结果。设计未说明必要前置条件、测试数据或清理，缺少有意义预期或可观察断言，以及需求/决策冲突或不安全操作，属于 executability（设计可判定性）/ conflict / safety 并阻断设计审查。ready 为“设计审查完成”，blocked 为“设计审查受阻”；checking、blocked、unknown 均不能进入执行准备。缺少实际执行器不是设计阻断依据，默认严格设计门禁不变。
- execute 仅核对和执行勾选的已有用例，不自动生成、补齐或修正；默认门禁拒绝时返回明确提示。填写地址不代表授权修正。repair 才进入生成/修正流程。相同输入可复用并继续显示同一拒绝，不自动反复修到合格；规则版本变化使旧缓存失效，但不保证旧任务即时修好或改写历史证据。

## 能力边界

浏览器协议使用版本化能力清单及完整用例定义规划，支持 click、fill（可为空）、clear、focus、受限 press，以及文本、显隐、启用状态、焦点、值、白名单属性与站内 pathname 断言。源码中的 browser-v3 执行器另含有界视口、几何/样式、图片加载、声明字体加载、中心点无遮挡和同源请求计数原语；每份计划至多 60 步，至少一个真实断言，总执行预算 120 秒（包含启动及证据，不含模型规划）。并行改造的 worker 协议标记同步与最终回归状态、全部数值及原语限制见全流程文档第 8 节。不能省略原设计要求来满足预算；新增原语不等于完整旧用例已解锁。协议变更使有指纹的旧浏览器脚本和证据失效，不会自动改写历史无指纹记录。

浏览器受阻原因单独保存 capability（缺能力）、environment（缺环境）、authorization（缺授权）、manual（确需人工）、unknown（待核对）及可选的缺失能力标识；旧状态仍兼容 manual/blocked，但不再把它们全部解释为真正人工项目。模型分类是规划结论，不是确定性环境认证；旧记录不根据输出文字猜测分类。实际失败另区分操作、断言、导航、浏览器和安全策略。任一受阻均不计为执行通过。

本轮未授权真实或虚构密码及令牌输入；运行时拒绝可识别的敏感字段交互及文本/值读取，安全元数据断言不授权读取秘密，策略拦截不截图，不能视为完整的敏感信息识别或操作系统沙箱。被测站点及测试数据仍须可信且隔离。协议不接受任意 JavaScript、跨站请求、网络故障注入、自动环境准备或安全绕过；同源请求观测仅计触发前登记后、指定窗口内的请求尝试数，不验证响应或数据库副作用。视觉基线、密码管理器及真实参与者研究仍需后续专项能力或人工证据。字段守卫不能保证识别未标注秘密，也不能保证业务点击无副作用。

结构覆盖是确定性检查，设计语义质量由模型分批评审，并非形式化证明或独立人工审计。默认模式严格检查全量，自定义仅核对选中范围的设计可判定性、冲突与安全并保留质量警告，不认证运行环境。当前执行准备只做结构、用例/断言声明及 runner 等检查，没有完整脚本语义一致性认证，不能保证测试脚本真实实现了用例设计；尚无通用的环境、测试数据、账号自动预检，不承诺自动准备环境或创建数据、账号。基线仍最多 50 项，用例上限保护成本，不意味着任意规模完整覆盖。执行超时不因用例类别改变；正常退出仍不能完全排除测试跳过或断言不足。完整环境版本认证、结构化报告解析、人工证据认证、偶发失败统计、环境隔离、专项性能执行器、结构化阈值、条件触发及基线签署尚未完善。自定义范围确认不等同于生产发布审批或合规豁免。
