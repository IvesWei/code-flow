# 测试分类、执行与验收策略

## 核心原则

生成范围、执行范围、阻断范围分开管理。用例类别回答“测什么”，优先级回答“先测什么”，执行策略回答“本次是否运行”，门禁策略回答“不通过是否阻断”。性能效率测试属于非功能测试，不天然低优先级，也不天然非必验。

本规则适用于开发任务自测，不代表生产发布审批或完整 SLA 认证。总体流程见 [用例生成与验收规范](acceptance-standard.md)。

从前端草稿、接口校验到逐条执行、证据与最终结论的完整步骤和硬限制见 [测试执行全流程与约束](test-execution-process.md)，包括文件优先且不自动回退、精确 runner 白名单、模型与浏览器不同超时、能力对照和未支持项。

## 字段规则

每条新用例的 `classification` 包含：

| 字段 | 取值 | 语义 |
| --- | --- | --- |
| testType | functional / performance / security / compatibility / reliability | 功能、性能效率、安全、兼容性、可靠性 |
| tags | 短标签数组，最多 20 项 | 如 smoke、regression、load、stress、soak、业务模块；不直接授权豁免 |
| priority | P0 / P1 / P2 / P3 | 执行排序建议，与是否阻断独立 |
| riskReason | 非空风险理由 | 业务影响、发生可能性及优先级依据 |
| executionPolicy | always / on_demand | 常规执行或用户显式按需选择；必验需求覆盖会覆盖按需建议 |

建议 P0 表示核心链路或重大数据、安全风险；P1 表示重要功能及明确质量目标；P2 表示一般补充验证；P3 表示低影响探索。平台当前保存和展示优先级，不依据优先级自动豁免，也尚不按优先级重排执行顺序。

`scenario` 仍是 normal、boundary、negative、permission、state，不能用它替代测试类别。性能用例同样可以验证正常负载、容量边界或异常恢复。

门禁策略 `gatePolicy` 不由模型自由填写。默认模式根据需求映射计算；自定义模式由用户显式确认的集合决定，选中为 blocking，未选中为 advisory。结果保存在 `testExecutionPlan` 中，并标记 default/custom 模式。

## 默认决策

| 条件 | 本次默认执行 | 门禁 |
| --- | --- | --- |
| 关联任何 required=true 需求 | 必须 | blocking |
| 需求映射缺失、引用未知需求 | 保守必验，同时结构校验拒绝 | blocking |
| 缺少 classification 的历史用例 | 必须 | blocking |
| 仅关联补充需求，executionPolicy=always | 执行 | advisory |
| 仅关联补充需求，executionPolicy=on_demand | 不选中，除非用户显式选择 | advisory |

轻量功能补充默认建议 always；探索性性能或长期稳定性专项默认建议 on_demand。这些是生成建议，不是按类别强制豁免规则。用户显式选择补充项后，它仍然是 advisory。

在默认模式中，`required=false` 只能表示明确标注为建议的补充验证。模型不能因成本、类别或缺少环境降低明确要求的等级。有歧义通过 ask_user 确认，问答保存在任务中。用户可切换到自定义必验、调整本次验收集合，填写范围理由并确认未选需求风险；该操作不修改需求基线，不等同于变更 SLA、合规义务或生产发布批准。

## 用例管理界面

- 需求功能点分组：新基线提供 feature 名称，同功能点统一命名。旧基线无 feature 时按“需求 ID + 验收条件”兜底，不修改或重新生成旧用例。
- 单条用例以首个关联需求作为主分组，详情保留全部关联需求；搜索可找到其他关联功能点，避免跨需求用例重复计数。
- 生成用例与用例执行为纵向独立模块，不提供标签切换。生成模块始终按设计审查筛选，保留类别、关键字、每页 10/20 条分页、功能组及步骤断言形式。执行模块集中展示启动操作、预览地址、持久化计划选中清单及运行证据，独立筛选分页；修改设计模块的待提交范围不改变已提交执行清单，运行 passed 不代表设计审查合格。执行输出及脚本默认折叠，可跨页定位设计用例。无计划不推断完整范围，历史运行单独标注，第一版不提供多轮归档。
- 规划页逐条设计状态只读取 `acceptanceAssessment.caseReviews` 的显式记录：unreviewed（待审查）、reviewing（审查中）、qualified（审查通过）、warning（存在质量提示）、rejected（审查不通过）、unknown（审查未完成）。旧记录缺失时为 unknown，不由聚合结果、未列入问题或运行 passed 推断通过。自定义 `executionAssessment` 的范围核对独立展示，不覆盖默认单条状态。
- 自测提示区分“正在生成用例”“正在审查用例”“正在核对自定义范围”；自定义核对不是再次生成，也不新增顶层任务阶段。
- 旧用例缺少分类时明确标记“未分类”，不凭标题自动猜测功能或性能类别；筛选“未分类（旧用例）”查看。
- 自定义模式支持逐条勾选、功能组批选；组批选只影响当前过滤匹配成员，包括其他分页上的匹配成员。跨页、跨筛选保留选择，切换任务隔离选择。改变集合或理由后需重新确认。

示例：核心接口在约定负载下满足 P95 响应时间阈值属于必验性能；没有约定阈值的最大吞吐量探索属于补充性能；长时间稳定性验证是否必验取决于需求约定，而不是 soak 标签本身。

## 生成与质量门禁

先补齐所有必验需求的适用场景，再使用独立补充预算。默认每批 8 条，总上限 300 条，补充上限 16 条。

| 环境变量 | 默认 | 范围 |
| --- | --- | --- |
| SELF_TEST_BATCH_SIZE | 8 | 1 至 20 |
| SELF_TEST_MAX_CASES | 300 | 1 至 1000 |
| SELF_TEST_OPTIONAL_MAX_CASES | 16 | 0 至 1000 |

补充预算也受总上限约束；设为 0 不追加补充用例，不删除已有用例。必验缺项仍拒绝，补充缺项只记录日志并保留在覆盖结果中。参数非法停止规划；修改配置后重新加载后台。

默认模式仍要求全量结构、必验覆盖与分批设计质量评审 qualified，严格规则不变。自定义仅核对勾选的已有用例的设计，不要求覆盖未选需求，不自动生成或修复；设计质量 status 与设计审查 readiness 分开，尚不支持任意编辑底层判定规则。设计审查依据需求、已确认决策和用例定义，不读取测试文件来认证脚本与断言一致性，也不因缺少文件、URL、runner 或实际环境而拒绝设计。

范围问题保存为 `findings`（code、category、message、caseIds）。coverage / quality 为警告，包括覆盖缺口、映射或分类不完整、较弱断言；较弱不等于无断言，仍须能观察并判定结果。executability（设计可判定性）/ conflict / safety 为设计阻断，包括设计未说明必要前置条件、数据或清理，没有有意义预期或可观察断言、与需求或已确认决策冲突及不安全操作。普通质量警告不能改报为设计阻断，设计不可判定、冲突或安全问题也不能降为警告；实际执行器或环境不可用留给执行阶段处理。

`executionAssessment.readiness` 取 checking / ready / blocked / unknown。ready 显示“设计审查完成”，blocked 显示“设计审查受阻”；仅完整设计核对后的 ready 允许进入执行准备，不代表环境可执行。允许 `status=rejected` 与 `readiness=ready` 同时存在，表示保留质量警告但没有设计阻断，不表示严格设计质量通过，也不表示已经通过测试。

质量评审保存 caseIssues（caseId、message）。修正仅涉及这些 ID、结构不合法项或确实需要修复的执行失败项；旧评审从 issues 中的明确 TC 编号兼容提取。没有明确编号的全局问题保留为全局评审反馈，不因此重写所有未执行用例。用例修正后重跑默认质量评审。

基线提取、生成与评审按阶段和批次使用独立短会话，输出作为版本化产物落库。默认和自定义评审每批保存结果及部分聚合；输入一致时重新发起操作仅请求未完成批次，超时不自动重发。已完成的拒绝结果仍是拒绝，不能因缓存复用绕过门禁。来源、代码、用例、范围、模型或规则变化使旧评审失效，执行前再次核对版本。完整契约及权限边界见 [自测实现链路](self-test-flow.md)。

“修正用例设计”和“审查并执行所选用例/启动浏览器自动化”是独立意图。审查中断后主操作显示“继续审查所选用例”。execute 不生成、补齐或修正用例；默认门禁拒绝时返回明确提示，要求用户选择修正或确认自定义集合。修正需要明确 repair 操作，不能因填写测试地址隐式触发。“接受当前风险”仅记录风险接受，不解除阻断、不启动执行。

界面顶部显示当前范围的设计审查结论、阻断数量、明确关联的用例数量及非阻断提示数量。阻断默认展开，提示默认折叠；默认严格门禁下的问题仍阻断，自定义按结构化类别区分，未分类历史问题保守显示待核对。重复的 findings、issues、caseIssues 合并展示并保留来源原文。用例编号可跨筛选和分页定位；“仅看阻断”在设计阶段按审查问题筛选，含全局问题时包含对应范围，执行阶段按实际准备受阻、人工确认、失败及未执行等结果筛选。

自定义列表的当前结论仅使用与当前集合、理由及提交时间匹配的 executionAssessment 逐条结果，未选中项显示“未纳入本次范围”；修改范围后当前结论变为未完成，但保留独立标注的上次审查参考、问题定位与历史阻断/状态筛选，已取消选中的问题不会消失。没有自定义审查时可参考默认审查，始终沿用默认严格分类；历史结果不放行当前范围，调整后必须重新确认并提交。默认审查保留在折叠区域。执行阶段独立汇总准备受阻、人工确认、执行失败和通过，不根据未知失败文本猜测为断言失败，也不覆盖已完成的设计审查。

## 执行计划与结论

执行前持久化计划版本、时间、用例 ID、是否选中、阻断策略与原因。选中项按现有执行器运行；未选中项保留原始状态，不改成 passed 或 skipped。界面分别展示必验通过数、补充失败数、补充未验证数和本次未选中数。

设计审查与执行准备分开。文件、URL、runner 和实际环境条件由执行阶段检查或在运行中暴露；已有测试文件无需属于本次 Git 变更。当前执行准备仅包含路径/文件和脚本支持范围等结构检查、用例/断言声明检查及本地 runner 检查，没有完整脚本语义一致性认证，不能保证脚本实现了声明的业务断言。没有通用的环境、测试数据或账号自动预检，也不会自动启动服务、安装依赖或创建账号。执行准备受阻记为 manual/skipped，不反写默认或自定义设计审查结果；设计结论不因这些运行状态改变，实际通过仍需执行证据。

执行计划保存基线/评审产物引用和输入指纹；新通过证据绑定需求、用例、代码与目标 URL，版本变化后重新验证。历史无指纹的通过证据兼容保留并记录来源不可追溯警告，不声称已完成历史版本认证。当前代码快照覆盖 Git 管理和未忽略文件，未认证全部忽略文件、外部依赖或远端服务状态。

用户在自动执行结果区勾选尚未执行的按需补充项，然后点击“执行选中补充项”。自测接口支持 `selectedCaseIds` 数组，只允许已保存、pending 或 manual 的用例，拒绝未知、重复或已执行的 ID。已有必验项仍在执行范围内，已通过证据不重写；选择不自动启动服务或安装专项工具。

默认 SUCCESS 要求：默认用例设计验收 qualified，至少一条 blocking 用例，所有 blocking 用例 passed，工程检查全部通过。补充失败或未验证不影响这个结论，但保留警告，不能宣称全部测试通过。

自定义 SUCCESS 要求：用户显式确认的非空已有用例集合，完整只读范围设计核对后 readiness=ready，完成执行准备且所有选中用例实际 passed，工程检查全部通过。范围质量 status 仍可 rejected，覆盖或质量警告随结果保留。界面和执行记录标为“自定义范围通过，不代表全部需求通过”，不是全量验收。未选用例原始状态与默认评审结果原样保留；不会覆盖默认拒绝，符合版本条件的已有 passed 证据可沿用，不自动重复执行。

自定义选择保存 acceptanceSelection（集合、理由、确认时间）与 acceptanceSelectionHistory；对应范围核对单独保存 executionAssessment（含 caseIds、status、readiness、findings、caseReviews），执行计划标记 custom。恢复默认提交 acceptanceSelection:null，记录日志，不删除过往选择。恢复编码后清除当前选择及范围评审，避免新代码沿用旧验收范围，历史记录保留。

接口示例（任务归属与登录校验仍有效）：

```json
{
	"intent": "execute",
	"automationUrl": "http://127.0.0.1:4173",
	"acceptanceSelection": {
		"mode": "custom",
		"caseIds": ["TC-01", "TC-03"],
		"reason": "本次仅验收核心功能，容量专项另行验收"
	}
}
```

未传 intent 的旧接口请求默认 execute，不隐式修正。repair 显式请求生成或修正；自定义不得为空，不允许未知、重复或 invalid 用例。与 selectedCaseIds 的补充执行选择不同，custom 的 caseIds 可以选已有 passed 或失败项，选中项为本次阻断集合。

必验项失败、manual、skipped 或环境不足进入 REVIEW。人工接受风险进入 ACCEPTED，不等于 SUCCESS，不删除原始证据。当前没有人工证据录入后将必验项认证为 passed 的功能。

历史用例没有分类时默认沿用全部必验；用户可显式自定义范围，定点修复不会为它自动补分类并降级。已有历史状态不自动重算，只在后续流程按所确认模式判定。已开始的旧工作器不会回溯撤销已经完成的修正，更新代码也不还原用户任务数据。

相同输入可复用并继续显示同一拒绝；重复 execute 不会授权修正，也不自动反复修到合格。当前规则版本为 `isolated-self-test-v3-design-review`，旧规则缓存不复用，但不会即时重算或修好旧任务。逐条状态、findings 和 readiness 沿用现有版本化 JSON 状态、快照与产物存储，不新增表或列，不需要 DDL 或数据库 schema 升级，不回填真实任务。

## 性能验收条件

明确的性能验收用例至少应描述：指标与单位、阈值及出处、负载模型、并发或到达率、持续时间及采样窗口、数据规模、测试环境和测量结果。P95、吞吐量、错误率、资源占用不可互相替代。

没有约定阈值的探索用例可以报告测量结果，不能编造 SLA 或声称已经达标。缺少约定负载或环境时，应补充确认，不应拿本机偶发耗时替代正式性能验收。

当前运行器仍是普通单文件测试及受限浏览器自动化，单文件超时仍为 120 秒。性能标签不会自动赋予压测能力、延长超时或认证阈值。已实现代码/输入指纹绑定，暂未接入性能专项工具、结构化指标与报告判定、长期稳定性调度、条件触发策略或环境隔离。

browser-v3 源码中的请求次数观测只按同源 pathname 和 method 累计触发前登记后的请求尝试，不能认证响应成功、业务幂等、P95 或数据库写入次数；60 步和 120 秒浏览器总预算也不是性能验收负载模型。协议接入复核状态见全流程文档第 8 节。自测独立入口沿用已有工程 checks，不应将自测重试描述为已重新跑过工程 test/build。

## 后续落地顺序

1. 已实现：分类与风险字段、功能点分组及筛选分页、定点质量修复、执行/修正分离、默认/自定义集合确认与审计、独立范围评审和范围限定成功结论。
2. 后续：基线逐项签署、审批角色与合规强制项、阶段和变更范围触发、人工验收证据、可配置的底层质量规则。
3. 后续：性能专项执行器、环境准入与负载安全限制、指标阈值模型、结构化测试报告、完整环境版本认证及偶发失败统计。
