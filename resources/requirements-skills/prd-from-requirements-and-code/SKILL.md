# PRD From Requirements And Code

将零散需求、现有系统证据和产品确认结果收敛为可评审、可实现、可验收的PRD，并生成经过结构与内容校验的Word文档。

## 核心原则

1. **证据分层**：始终区分“需求原文”“代码现状”“用户确认”“合理推导”，不得把推测写成定稿规则。
2. **先澄清再定稿**：影响数据模型、状态机、角色权限、唯一键、跨模块关联或历史数据的歧义，必须询问用户。
3. **边界必须闭合**：正常路径之外，覆盖重复、空值、并发、撤回、删除引用、角色离职、通知失败、历史兼容等场景。
4. **代码是现状证据，不是需求真相**：代码用于识别已有能力和改造差距；目标行为以用户确认后的PRD为准。
5. **验收可执行**：每条关键规则都应能转换为接口校验、UI行为或测试用例。
6. **Word是正式交付物**：Markdown可作为中间稿，但最终必须输出可打开、可检索、结构完整的`.docx`。

## 输入

至少需要以下输入中的两类；缺失时先向用户索取：

- 需求原文、会议纪要、流程图、旧版PRD或原型。
- 当前代码库或可定位的模块、页面、接口。
- 目标版本、范围、明确不做事项。
- 文档元信息：标题、日期、状态、作者/评审人（可按用户要求省略）。

## 工作流

### 阶段一：建立任务边界

1. 阅读所有附件和用户要求，提取：
   - 目标版本与业务目标。
   - 涉及模块、角色、流程、字段、外部系统。
   - 删除线、批注、“待确认”“建议”“是否”等不稳定信息。
   - 明确的范围外内容。
2. 若用户提供旧版PRD，确认它是：
   - 仅作为章节结构参考；或
   - 需求基线，需要继承并增量修改。
3. 明确最终交付位置和文件名。默认：`docs/<产品>_<版本>_<主题>_PRD.docx`。

### 阶段二：定向读取代码现状

遵循“最小充分证据”，优先定位：

1. 菜单与路由：现有模块名称、入口、权限可见性。
2. 页面与组件：列表字段、搜索项、表单、校验、按钮权限、空状态。
3. API与类型：请求参数、返回模型、唯一标识、关联方式、状态字段。
4. 流程实现：节点、操作者、提交/打回/删除、通知触发。
5. 目标集成模块：调用方、任务详情、快照或实时引用方式。
6. 邻近测试或接口注释：已有约束和失败行为。

输出内部“现状证据表”：

| 需求域 | 代码锚点 | 当前行为 | 与需求冲突/缺口 |
|---|---|---|---|
| 示例：物料维护 | 页面、接口、类型文件 | 当前字段与权限 | 缺少字段、强关联或权限不符 |

不要为了“全面了解代码库”而泛搜无关目录。控制路径确认后立即进入差距分析。

### 阶段三：建立需求差距矩阵

按以下维度逐条对照需求与代码：

- 菜单与术语。
- 数据对象、主键、唯一键、关联粒度。
- 字段、来源、类型、必填条件、提示文案。
- 搜索、排序、分页、导入、导出。
- 新增、编辑、删除、停用、恢复。
- 角色、数据权限、字段权限、接口鉴权。
- 状态机、提交、打回、撤回、转交、催办。
- 通知事件、渠道、接收人、失败策略。
- 跨模块引用、实时数据、快照、刷新策略。
- 历史数据迁移、兼容和回滚。
- 审计、版本、变更记录。

将问题分级：

- **P0**：会改变数据模型、状态机、权限模型、唯一键、跨模块关联或迁移方案；未确认不得写定稿。
- **P1**：会影响主要业务规则或错误处理；应在定稿前确认。
- **P2**：交互参数或技术配置，可给推荐默认值并在评审关注项中保留。

### 阶段四：分轮澄清

使用结构化问题工具，每轮控制在6-9题。每题必须：

1. 只讨论一个决策。
2. 说明为何会影响PRD。
3. 提供2-4个互斥选项。
4. 标出基于代码与业务一致性的推荐项。
5. 允许自由输入。

建议顺序：

- **第一轮（P0）**：范围、对象粒度、唯一键、角色节点、完成机制、关联方式、实时/快照。
- **第二轮（P1）**：导入更新、错误策略、必填条件、权限、通知、删除引用、多版本。
- **第三轮（冲突收口）**：原文自相矛盾、特殊字段归属、无数据行为、多对象匹配、审计和元信息。

收到回答后形成“决策账本”，后续文档只能使用已确认答案。若新答案与旧答案冲突，以最新明确答案为准，并在必要时再次确认。

**禁止行为：**

- 用“建议”“一般”“可考虑”代替必须明确的规则。
- 将代码当前行为直接当作目标需求。
- 在存在P0未决项时生成“定稿”Word；最多生成标记待确认的讨论稿。

### 阶段五：补齐边界场景

至少检查以下清单，并把适用项写入PRD：

- 重复记录、大小写/空格归一、组合唯一与并发唯一冲突。
- 空文件、错模板、缺表头、非法行、部分成功、重复导入、幂等重试。
- 草稿、未提交、部分节点完成、撤回、上游变更导致下游回退。
- 角色离职、转交、多人并发编辑、越权直链和接口调用。
- 被引用数据的编辑、删除、停用和历史展示。
- 多对象匹配、部分匹配、零匹配、冲突匹配。
- 实时引用与快照、源数据更新、手动刷新及历史轮次。
- 通知去重、自通知、失败、重试、无效账号、过期链接。
- 长文本、特殊字符、大数据量、分页和性能上限。
- 旧数据迁移异常、幂等迁移、回滚和历史兼容。

更多质量门禁见[质量检查清单](./references/quality-gates.md)。

### 阶段六：编写PRD

使用[PRD结构模板](./references/prd-outline.md)，并遵循：

1. 先写背景、目标和范围，再写现状与目标方案。
2. 使用表格表达字段、权限、状态机、通知和验收标准。
3. 每个功能模块至少包含：
   - 入口与使用角色。
   - 列表/详情/表单能力。
   - 字段定义与条件必填。
   - 正常流程。
   - 权限规则。
   - 异常与边界。
   - 与其他模块的数据关系。
4. 状态流转写清“当前状态、执行人、动作、校验、目标状态、通知”。
5. 数据规则写清“业务唯一键”和“数据库兜底约束”。
6. 区分物理删除、逻辑删除、停用和历史快照。
7. 验收标准使用`AC-01`编号，描述“场景 + 预期结果”，覆盖所有P0/P1决策。
8. 最后添加发布建议、风险依赖和仍需技术评审的参数项。

### 阶段七：生成Word

1. 优先使用`python-docx`。若不可用：
   - Windows先尝试`py -m pip install python-docx`；
   - 不要误用Microsoft Store的`python.exe`占位程序；
   - 无法安装时向用户说明，并交付Markdown中间稿。
2. 使用[DOCX生成器](./scripts/render_prd_docx.py)将Markdown中间稿转为Word：

```powershell
py .github\skills\prd-from-requirements-and-code\scripts\render_prd_docx.py `
  --input docs\prd-draft.md `
  --output docs\product_v7.6_PRD.docx `
  --title "产品 V7.6" `
  --subtitle "主题产品需求文档（PRD）" `
  --date "2026-09-11"
```

3. Word格式要求：
   - A4页面、合理页边距、页眉、页码。
   - 封面、修订记录、目录域。
   - 标题层级可生成目录。
   - 表头突出、跨页重复、表格不超出版心。
   - 中文字体使用微软雅黑或等价可用字体。
   - 不嵌入失效的外链图片；必要时先下载为本地资源。

### 阶段八：验证交付

生成后必须执行至少三类检查：

1. **可打开性**：使用`python-docx`重新打开文件。
2. **包结构**：执行`py -m zipfile -t <file.docx>`。
3. **内容完整性**：同时读取普通段落和所有表格单元格，检查：
   - 核心章节均存在。
   - P0决策关键词均存在。
   - 验收标准数量与关键需求匹配。
   - 文档段落、表格和文件大小非异常。
4. **视觉检查（环境允许时）**：用Word/LibreOffice转PDF或预览，检查目录、分页、表格宽度、孤行和中文字体。
5. 清理一次性脚本和中间文件；保留用户需要的Markdown源稿、正式DOCX及必要资源。

## 最终回复

最终回复应简洁包含：

- 可点击的DOCX路径。
- 文档覆盖的主要模块。
- 已完成的验证。
- 仍存在的明确限制（例如未能视觉预览），不得隐藏。

不要重复整份PRD，也不要声称未经验证的“格式完美”。
