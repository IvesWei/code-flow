# PRD From Requirements And Code

将需求材料、代码现状和用户确认结果收敛为两份配套PRD：业务评审版与开发规格版。本 Skill 是**唯一的 PRD 正文与 Word DOCX 输出出口**，严格使用[固定双模板](./references/prd-outline.md)，不得自创章节或沿用旧版带封面/目录/宽表的单版结构。

### 与 UI 设计图 Skill 的分工与协同

- **无需新建 UI 设计稿时**：本 Skill 独立运行；使用用户已提供的本地图片，无图片时在所属功能的`设计稿：`下原位写`待确认：尚未提供设计稿`。
- **用户要求包含 UI 设计稿 / 交互原型截图时**：联用 [prd-with-ui-design-delivery](../prd-with-ui-design-delivery/SKILL.md) 协同完成，严格遵循单次取证、上下游交接顺序：
  1. **共享一次取证与澄清**：合并执行阶段二代码现状回溯（含路由→Layout→菜单→页面容器）与阶段四 P0/P1 结构化提问，禁止向用户重复提问；
  2. **先定功能与编号框架**：先按本 Skill 确定模块、功能划分及开发规格版 `FR-xx` / `AC-xx` 编号；
  3. **调用 UI Skill 产出设计图**：由 `prd-with-ui-design-delivery` 产出 `index.html`、`ui-manifest.json`（绑定 `FR / AC` 编号）和经像素检视通过的 `screenshots/*.png`，运行其 `validate_ui.py --require-prd-links`；
  4. **回填双版并统一渲染校验 DOCX**：由本 Skill 将定稿 PNG 嵌入两版对应功能的`设计稿：`小节，使用 [render_prd_docx.py](./scripts/render_prd_docx.py) 生成双版 `.docx`，并用 [validate_prd_delivery.py](./scripts/validate_prd_delivery.py) 完成双版追溯与内嵌图片哈希校验。

## 核心原则

1. **固定双版**：一次完整处理必须交付业务评审版和开发规格版，不能合并成一份或只交付其中一版；默认生成两份DOCX，用户要求Markdown时生成两份Markdown。
2. **只有标题与大纲树**：标题后直接进入第一个模块；禁止封面、目录、修订记录、版本行、阅读指引、方案概述、独立章节、功能/字段宽表、确认栏、签字表或集中拍板问题。
3. **功能自包含但不重复**：行为、字段、状态、设计稿、规则均挂在所属功能下；异常场景与边界条件、权限与AC仅出现在开发规格版的所属功能下。一个事实只完整定义一次，共用内容短引用，不为自包含而全文复述。不得另设通知、迁移、审计或验收章节。
4. **证据不等于目标**：内部区分需求原文、代码现状、用户确认与推导。代码用于取证，不得把当前实现或推测直接写成目标规则。
5. **先澄清再定稿**：重要歧义通过对话工具询问，不把问卷放入PRD；未解决项就地写成“待确认：……”陈述，不得编造或默认放行权限。
6. **两版业务一致、详略分工明确**：模块、功能、场景、状态和设计稿的顺序及业务口径一致；业务评审版聚焦**本期实际发生修改与调整的增量内容**（功能名称下方的系统行为只写本次新增/调整的变化，禁止写入“其他未改任务类型/模块维持原逻辑”、原有未变前置步骤或一串“不新增××”等非变动说明；不设异常场景与边界条件、权限与验收标准小节；仅输出界面增删改字段与界面看不出的后端复杂逻辑，无对应项整节省略）；开发规格版原位补齐防回归范围边界、开发/测试对接所需的字段、BR规则、EX异常、编号、权限与AC，不要求两版小节或文字机械相同。
7. **验收可执行**：开发版每条AC采用Given-When-Then、具体数字示例与FR/BR/EX关联；未确认的关键规则不得伪装成可执行定稿。
8. **产品语言与最小充分表达**：先讲用户能做什么、操作后有什么变化，再写必要限制。简单功能一句话说清，不混入代码排查、设计论证、实现步骤或无关的“不新增”声明；结构完整不等于每节都要写满。

## 输入

读取用户已提供的需求材料与代码范围；材料不足以确定业务含义时再询问，不按材料类别数量机械拦截：

- 需求原文、会议纪要、流程图、旧版PRD或原型。
- 当前代码库或可定位的模块、页面、接口。
- 目标版本、范围、明确不做事项。
- 输出格式、标题、交付路径与文件名。产品版本可包含在标题和文件名中，不生成独立文档版本、日期、作者或评审人行。

## 工作流

### 阶段一：建立任务边界

1. 阅读所有附件和用户要求，提取：
   - 目标版本与业务目标。
   - 涉及模块、角色、流程、字段、外部系统。
   - 删除线、批注、“待确认”“建议”“是否”等不稳定信息。
   - 明确的范围外内容。
2. 若用户提供旧版PRD，确认需要继承的业务内容和本次变更范围；旧版结构不得覆盖固定双模板。
3. 明确格式与两份文件名，默认：
   - `docs/<产品>_<版本>_<主题>_PRD_业务评审版.docx`
   - `docs/<产品>_<版本>_<主题>_PRD_开发规格版.docx`
   - 用户指定Markdown时将扩展名改为`.md`；要求两种格式时各交付双版。

### 阶段二：定向读取代码现状

遵循“最小充分证据”，优先定位：

1. 菜单与路由：从路由表（如 `routes.tsx`）出发，完整回溯“路由路径 → 绑定的 Layout 布局壳子（区分顶栏/侧栏宽度/无侧栏路由组）→ 侧栏或顶栏菜单配置 → 面包屑与权限可见性”，锁定页面的真实外壳坐标，禁止跳过父级布局直接只读局部子组件。
2. 页面与组件：从页面根容器顺着 Tab、分栏、折叠区定位到目标子组件/弹窗，记录目标区域在整页中的纵向位置（首屏或中下屏）、相邻筛选栏、表格列序、表单校验、按钮权限与空状态，同时核对全局/页面级样式覆盖层。
3. 运行态基线（可用时优先）：若本地开发服务已启动或用户提供了可访问环境/登录态，优先通过浏览器或截图核对真实运行态页面结构与布局尺寸作为现状基线，不得凭印象脑补页面导航壳子。
4. API与类型：请求参数、返回模型、唯一标识、关联方式、状态字段。
5. 流程实现：节点、操作者、提交/打回/删除、通知触发。
6. 目标集成模块：调用方、任务详情、快照或实时引用方式。
7. 邻近测试或接口注释：已有约束和失败行为。

建立内部“现状证据表”，不把该表或取证过程插入交付PRD：

| 需求域 | 代码锚点（含路由与Layout） | 页面区块坐标与当前行为 | 与需求冲突/缺口 |
|---|---|---|---|
| 示例：物料维护 | 路由、Layout、页面容器、接口、类型文件 | 所属菜单层级、所在Tab/屏位、当前字段与权限 | 缺少字段、强关联或权限不符 |

不要为了“全面了解代码库”而泛搜无关业务模块；但对目标页面所属的路由、Layout 壳子和直接父容器必须取证闭合后再进入差距分析。

### 阶段三：建立需求差距矩阵

按以下维度逐条对照需求与代码：

- 菜单与术语。
- 数据对象、主键、唯一键、关联粒度。
- 字段、来源、类型、必填条件、提示文案。
- 搜索、排序、分页、导入、导出。
- 新增、编辑、删除、停用、恢复。
- 角色、数据权限、字段权限、接口鉴权。
- 状态机、提交、打回、撤回、转交、催办。
- 通知事件、渠道、接收人、失败策略。
- 跨模块引用、实时数据、快照、刷新策略。
- 历史数据迁移、兼容和回滚。
- 审计、版本、变更记录。

将问题分级：

- **P0**：会改变数据模型、状态机、权限模型、唯一键、跨模块关联或迁移方案；未确认不得写定稿。
- **P1**：会影响主要业务规则或错误处理；应在定稿前确认。
- **P2**：交互参数或技术配置，可在对话中推荐取值；未经确认时在所属功能内标注“待确认”，不新增评审关注项章节。

### 阶段四：分轮澄清

使用结构化问题工具，每轮控制在6-9题。每题必须：

1. 只讨论一个决策。
2. 说明为何会影响PRD。
3. 提供2-4个互斥选项。
4. 标出基于代码与业务一致性的推荐项。
5. 允许自由输入。

建议顺序：

- **第一轮（P0）**：范围、对象粒度、唯一键、角色节点、完成机制、关联方式、实时/快照。
- **第二轮（P1）**：导入更新、错误策略、必填条件、权限、通知、删除引用、多版本。
- **第三轮（冲突收口）**：原文自相矛盾、特殊字段归属、无数据行为、多对象匹配、审计和元信息。

收到回答后形成内部“决策账本”。若新答案与旧答案冲突，以最新明确答案为准，并在必要时再次确认。问题、选项、决策账本和证据表均属于工作过程，不是PRD章节。

**禁止行为：**

- 用“建议”“一般”“可考虑”代替必须明确的规则。
- 将代码当前行为直接当作目标需求。
- 存在P0未决项时声称定稿；需要先交付时仍输出同构双版，并在相关字段、规则、权限或异常下就地标注“待确认”，在交付回复中说明限制。

### 阶段五：补齐边界场景

以下是内部检查清单，不是正文扩写清单。只把与本次变更有关、会影响业务结果的适用项写入所属功能，不逐功能复制通用场景，不扩展模板小节：

- 正常、加载中、空数据、请求失败、业务异常、无权限和重复操作。
- 重复记录、大小写/空格归一、组合唯一与并发唯一冲突。
- 空文件、错模板、缺表头、非法行、部分成功、重复导入、幂等重试。
- 草稿、未提交、部分节点完成、撤回、上游变更导致下游回退。
- 角色离职、转交、多人并发编辑、越权直链和接口调用。
- 被引用数据的编辑、删除、停用和历史展示。
- 多对象匹配、部分匹配、零匹配、冲突匹配。
- 实时引用与快照、源数据更新、手动刷新及历史轮次。
- 通知去重、自通知、失败、重试、无效账号、过期链接。
- 长文本、特殊字符、大数据量、分页和性能上限。
- 旧数据迁移异常、幂等迁移、回滚和历史兼容。

更多质量门禁见[质量检查清单](./references/quality-gates.md)。

### 阶段六：编写PRD

使用[PRD结构模板](./references/prd-outline.md)，并遵循：

1. 先用统一的业务事实写业务评审版，再派生开发规格版，补齐开发/测试对接所需的字段、BR规则、编号、校验层级、数据影响、权限与AC；不把工程说明或设计稿/界面已能直观体现的逻辑换词后塞进业务版。逐功能核对业务含义，不要求两版逐字或逐小节相同。
2. 每份文档只有一个标题。每模块一棵连续大纲树，符号与层级固定为`● → ○ → ■ → ■ → ■`；两空格缩进一级，不使用独立小标题或表格。
3. 功能行仅加粗功能名称，后接不加粗的对应场景与功能描述。模块行和各小节引导行加粗；系统行为、字段、枚举、规则和异常子条目均不加粗。
4. 每个功能按固定顺序组织：系统行为、该功能涉及的字段（业务版按界面变更可选）、状态流转（仅流程类保留）、设计稿、业务规则与生成逻辑（业务版按后端复杂逻辑可选）；开发版再依次接异常场景与边界条件、权限与验收标准。
5. 业务版不出现MOD/FR/FLD/TR/BR/EX/RM/AC编号，不设置异常场景与边界条件、权限或验收标准小节。功能名称下方的系统行为描述**只写本次需求涉及修改、调整的增量变化**，不写未改动的其他任务类型/模块“维持原逻辑”说明或既有未变操作步骤；“该功能涉及的字段”仅标出本次需求在原有用户操作界面上新增、删除、变更的字段（注明新增/变更/删除），不列未变动的原有字段或纯后端隐藏字段，无界面字段增删改时整节省略；“业务规则与生成逻辑”非强制输出，凡在设计稿或界面交互上能看出的逻辑均无需展示，仅在后端有复杂业务逻辑而前端仅展示一个字段或某项数据（如统计图核心指标的统计逻辑、复杂生成逻辑）时才输出，无则整节省略。
6. 开发版使用MOD、FR、FR-xx-n、FLD、TR、BR、EX、RM、AC编号，建立`MOD/FR → FLD/TR → BR/EX → AC`追溯链，保留开发/测试对接所需的字段与BR规则。编号唯一、引用可解析，更新文档时保留既有条目标识。
7. 每条BR注明校验层级（双端 / 仅后端），共用规则注明适用范围；开发版异常用“如果发生……，系统会……”句式，且每条EX注明数据影响（整体回滚 / 部分成功 / 只读保留）。无法确定时对应属性标“待确认”，不猜测。
8. 流转写清源状态、目标状态、触发事件、前置条件、触发角色和副作用；非流程功能删除整个状态流转小节。业务版无界面增删改字段或无后端复杂规则时直接整节省略对应小节，禁止保留空引导行或写“无/不新增字段”凑数；开发版固定小节保留，无适用内容时写明确陈述。
9. 开发版权限写清角色、操作可用/仅查看/不可见及数据范围，固定声明服务端强制鉴权、前端仅展示控制；权限不明时明确“待确认”，不得默认放行。
10. 每条AC采用Given-When-Then，包含具体数字示例、明确数据/状态/页面结果及关联FR/BR/EX编号，覆盖P0/P1决策和适用边界；不只写“符合预期”。
11. 设计稿图片插在所属功能“设计稿：”引导行下，每张图后跟同层级的一行图注。用户要求含UI设计稿时联用 `prd-with-ui-design-delivery` 生成经浏览器像素检查通过的本地PNG并回填；未要求且未提供设计稿时原位写“待确认：尚未提供设计稿”，不得伪造或引用失效图片。
12. 所有条目均为写好的方案陈述，不放模板占位符、问卷、解释性过渡文字、设计理由或附加总结。未决项必须就地标注“待确认”。

### 阶段六补充：表达与去重门禁

详细分工及正反例见[模板中的表达规范](./references/prd-outline.md#表达密度与信息归属)。生成两版前后均执行：

1. **先收敛功能**：一个独立用户目标对应一个功能。入口展示、字段校验、保存刷新、日志和通知不因模板要求自动拆成独立功能；只有能独立操作或验收的能力才单列。
2. **一句话概括**：功能名用动宾短语；场景只写何时使用；描述只写提供什么能力，不串列角色、规则、异常和范围声明。系统行为默认一条一句，简单功能不硬拆多条。
3. **各节只回答自己的问题**：行为写操作与反馈；字段写属性与来源；流转写状态变化；规则写约束与口径；异常写偏离正常路径的处理；权限写谁能操作；AC写具体样例。字段不复述流程，行为不提前铺开全部规则，异常不再讲一遍正常逻辑。
4. **一个事实一个定义**：数量阈值、候选范围、锁定条件、汇总公式等只在最合适位置完整定义；其他位置确需使用时只写可定位的短引用。AC以样例验证规则，不复制规则全文。
5. **只写本期增量**：业务评审版只描述本次修改、调整的目标对象与行为变化，严禁写入不涉及本次变动的其他模块/任务类型“不展示××、维持原逻辑”等排他说明、未变更的历史前置操作、代码排查过程和无业务增量的反向罗列（如“不新增××节点”）；防回归范围约束与排他校验统一放在开发规格版的 `BR-xxx` 规则中。
6. **骨架不等于篇幅**：业务版无界面字段增删改时整节省略“该功能涉及的字段”，无设计稿/界面之外的后端复杂逻辑时整节省略“业务规则与生成逻辑”，不留空引导行、不写凑数说明；开发版保留对接所需小节，不适用内容用一条简短陈述或已有规则引用收口，不造计算公式、编号规则、异常、字段或新功能。条目数量随复杂度变化，不设最低条数、不追求各功能等长。
7. **完成后做删除测试**：逐条判断“删掉后是否丢失独有的业务信息”。无损则删除或合并；不同触发条件即使结果相同也要保留区别。检查跨小节、跨功能的同义重复，而不只查相同句子。
8. **精简旧稿不改需求**：先核对已确认决策与既有AC，保留有效编号和图片关联；另存精简版，不覆盖用户原稿。对比有效正文长度并核验决策覆盖，不用字数指标替代业务完整性；UI未变时复用已有原型与截图，不声称重新验证了UI。

### 阶段七：按格式生成双版

1. 用户要求Markdown时直接交付经过校验的两份Markdown，不强制生成Word。源稿使用一个`# 标题`，随后使用上述符号与两空格缩进，每条占一行；不把整个大纲包在代码块内。
2. DOCX使用`python-docx`；Windows使用`py`，不要误用Microsoft Store的`python.exe`占位程序。缺少依赖时先说明并按仓库规则获得安装确认；无法生成Word时明确阻塞，只能交付双版Markdown，不能声称DOCX已完成。
3. 使用[DOCX生成器](./scripts/render_prd_docx.py)分别转换两份源稿，不拼接为一个文档。`--title`必须与源稿的唯一标题一致：

```powershell
py .github\skills\prd-from-requirements-and-code\scripts\render_prd_docx.py `
  --input docs\product_PRD_业务评审版.md `
  --output docs\product_PRD_业务评审版.docx `
  --title "产品 主题 PRD（业务评审版）"

py .github\skills\prd-from-requirements-and-code\scripts\render_prd_docx.py `
  --input docs\product_PRD_开发规格版.md `
  --output docs\product_PRD_开发规格版.docx `
  --title "产品 主题 PRD（开发规格版）"
```

4. Word格式要求：
   - A4页面、合理页边距、微软雅黑或等价中文字体。
   - 首段是标题，下一段直接是首个模块；无封面、目录、元信息表、解释性段落或独立章节。
   - 使用真正的五级Word大纲列表，符号为`●、○、■、■、■`，缩进与混合加粗规则与源稿一致。
   - 图片用`■ ![图1：功能说明](<本地图片路径>)`，下一行同级写`■ 图1：功能说明`；相对路径基于源稿目录，支持PNG/JPEG，不直接嵌入外链。
   - 图片不超出版心，图片与图注相邻；缺少图片或格式不合法时明确报错，不降级成文本或跳过。
   - 生成器只校验结构、列表格式与图片，业务语义、编号追溯和双版一致性仍须按质量清单核验。

### 阶段八：验证交付

按[质量检查清单](./references/quality-gates.md)逐项检查两版，并运行[双版交付校验工具](./scripts/validate_prd_delivery.py)执行自动化门禁（含UI设计稿时一并传入 `--manifest` 与 `--screenshots`，自动完成开发版编号对齐与DOCX内嵌图片SHA-256哈希比对）：

```powershell
$env:PYTHONUTF8 = '1'
py .github\skills\prd-from-requirements-and-code\scripts\validate_prd_delivery.py `
  --business-md docs\product_PRD_业务评审版.md `
  --dev-md docs\product_PRD_开发规格版.md `
  --business-docx docs\product_PRD_业务评审版.docx `
  --dev-docx docs\product_PRD_开发规格版.docx `
  --manifest docs\<主题>-prototype\ui-manifest.json `
  --screenshots docs\<主题>-prototype\screenshots
```

仅交付不含新建UI的DOCX时省略 `--manifest` 与 `--screenshots`；仅交付Markdown时再省略 `--business-docx` 与 `--dev-docx`。同时核验：

1. **可打开性与包结构**：`python-docx`重新打开与`py -m zipfile -t <file.docx>`均通过。
2. **结构、内嵌图与追溯链**：首段标题且次段模块；无表格、TOC域、封面分页或页眉。业务版零技术编号且无异常/权限/AC小节；开发版 `AC-01` 连续编号、BR校验层级、EX数据影响、服务端鉴权声明及 `MOD/FR → FLD/TR → BR/EX → AC` 引用全部闭合；所有本地图片真实内嵌进两份DOCX的 `word/media/`。
3. **双版语义一致性与表达质量**：逐功能核对场景、描述、行为、状态与设计稿的业务口径一致，并核对业务版保留的界面变更字段、后端复杂规则与开发版对应定义无冲突；执行表达与去重门禁，无凑数条目或同义重复。
4. **视觉检查（环境允许时）**：用Word/LibreOffice预览检查五级缩进、混合加粗、图片图注与分页；不可预览时如实披露限制。
5. **清理现场**：清理一次性脚本和中间文件；保留双版Markdown、DOCX及联用产出的原型与定稿图片。

## 最终回复

最终回复应简洁包含：

- 可点击的两版文件路径，标明业务评审版和开发规格版。
- 文档覆盖的主要模块。
- 已完成的验证。
- 仍存在的明确限制（例如未能视觉预览），不得隐藏。

不要重复整份PRD，也不要声称未经验证的“格式完美”。
