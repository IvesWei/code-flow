# PRD固定双模板

一次完整交付包含业务评审版与开发规格版。两版模块、功能及保留小节顺序统一、业务含义一致；业务评审版聚焦界面增量字段与设计稿/界面看不出的后端复杂逻辑（无对应项时整节省略），开发规格版保留完整对接字段、BR规则、编号、权限及验收标准，不要求逐字或逐小节机械复刻。以下说明用于编写，不复制为PRD正文。

## 公共输出约束

- 文档只有“标题 + 模块大纲树”两层组织。标题后直接进入首个模块，每个模块一棵连续树，同模块的多个功能按固定小节顺序组织。
- 禁止封面、目录、阅读指引、文档版本行、修订记录、方案概述、独立章节标题、过渡文字、一页速览、确认栏、签字表、集中拍板问题和问卷。
- 不用表格罗列功能、字段、状态、权限或验收。背景、现状证据、差距矩阵与决策账本仅用于内部分析；必要的业务信息融入对应功能，不另设章节。
- 导入、通知、审计、迁移、历史兼容、跨模块引用和性能约束按适用性放在所属功能的行为、字段、规则或异常下，不新增模板外小节。
- 状态流转仅流程类功能保留，非流程类整节删除。业务评审版的“该功能涉及的字段”和“业务规则与生成逻辑”均为条件保留，无适用内容时直接整节省略（不输出引导行，不留空也不写“无/不新增字段”）；开发规格版其余固定小节保留，确无字段或规则时写“本功能不新增或变更业务字段”等已确认陈述供研发核对，禁止留空引导行。
- 未确定事项原位写“待确认：具体未决内容”，不编造规则，不用疑问句或待填空占位符代替方案。
- 未提供设计稿且用户未要求生成UI时保留引导行，并写“待确认：尚未提供设计稿”；用户要求含UI设计稿时联用 `prd-with-ui-design-delivery` 产出本地截图后嵌入，每张图后紧跟一行图注。
- 业务版使用纯业务语言，不带技术编号，不设异常场景与边界条件、权限或验收标准小节；开发版不得改变已确认业务含义。

## 表达密度与信息归属

模板规定内容位置，不规定篇幅。以产品经理面向业务方说明方案的方式书写，先形成简洁业务稿，再补开发对接信息。

- **功能划分**：按独立用户目标划分，不按技术环节或模板小节拆功能。只是某功能的字段、校验、保存反馈或后台副作用时，留在该功能中；能独立操作或验收时才单列。
- **功能行**：名称用简短动宾短语；场景只交代触发时机；描述用一句话概括能力。不将同一句话换词写三遍，不把所有限制塞进功能行。
- **系统行为**：只写本次需求涉及修改、调整的用户操作与系统反馈变化。业务版严禁混入未改动前置步骤、不涉及本次变动的其他任务类型/模块“维持原逻辑”说明，或“不新增××”式的反向凑句（防回归排他边界归入开发版 `BR-xxx`）。默认一条一句，同一交互环节的紧凑联动可合并为一句，不设置最低条数。
- **字段**：业务版只标出本次需求在原有用户操作界面上新增、删除、变更的字段（注明【新增】/【变更】/【删除】及填写要求、默认值、枚举等变化），不输出未变动的原有字段或纯后端技术字段，界面无字段增删改时整节省略；开发版补充开发/测试对接所需的接口、持久化与标识字段。不在行为中复述字段属性。
- **状态流转**：源状态、目标状态、触发条件、角色与必要联动。不在行为、规则、异常中重复完整描述同一状态变化，相关位置使用短引用。
- **业务规则**：业务版不必强制输出，只要在设计稿或界面交互上能看出的逻辑（如常规必填、枚举选择、显隐联动、普通输入限制）均无需展示，仅在后端有复杂业务逻辑而前端仅展示一个字段或某项数据（如统计图某项核心指标的统计逻辑、复杂自动计算/编号生成规则）时才输出，否则整节省略；开发版保留完整的校验规则、计算/生成规则及数据保护规则供开发实现与AC追溯。一个事实只完整定义一次；其他功能引用其名称或编号并只写差异。
- **异常**：仅在开发规格版保留，描述偏离正常路径时的反馈、恢复方式和数据影响（业务版因用户操作相关边界与异常已在设计稿和交互中体现，整节不输出）。不能把正常成功流程、字段定义或规则的反向说法直接再写一遍；同一校验失败的反馈可合并，恢复方式不同的异常须保留。
- **权限与AC**：权限写角色、操作及数据范围；AC写最小而具体的输入、动作、可观察结果和引用，不把全部规则改写成另一段说明。不为每条文案或每个字段机械增加AC。
- **原位短引用**：仅在读者需要该规则时引用，不能把每个小节变成“详见……”列表。业务版写明确功能名/规则名，开发版写稳定编号，不另设公共规则章节。
- **无变更内容**：业务版直接省略未改动模块、其他任务类型“维持现状”的排他说明以及既有未变流程步骤；开发版仅在 `BR-xxx` / `AC-xxx` 中保留防止误改其他类型的接口/权限边界。删除排查过程、设计理由与通用工程口号。
- **长度判断**：一句能说清就不写一段；复杂条件可分条，不用硬性字数截断前提、例外、权限或回退条件。业务版无适用字段或复杂后端规则时直接整节省略；开发版固定小节无适用内容时一条简短说明即可，不为填骨架发明需求。

例如，反例是把未改动的旧字段全部抄进业务版，并把界面上已能直观看到的校验与异常规则在行为、字段、规则和异常中重复多遍。业务版应按如下分工精简（不输出“异常场景与边界条件：”小节；若无界面看不出的后端复杂逻辑，直接省略“业务规则与生成逻辑：”整节）：

```text
    ■ 管理员可新增、删除或替换待审批人，已审批人员锁定不可改。
    ■ **该功能涉及的字段：**
      ■ 【变更】审批名单 —— 人员多选，支持在审批中增删或替换未审批人员。
    ■ **状态流转：**
      ■ 审批发布 → 审批通过：保存后剩余人员均已通过时自动推进。
    ■ **设计稿：**
      ■ ![图1：变更审批人弹窗](<assets\变更审批人.png>)
      ■ 图1：变更审批人弹窗。
```

不要为了“精简”只写“按现有规则处理”，却丢失本期独有的锁定范围、总人数口径、补审范围或通知失败处理。

## 大纲、缩进与加粗

源稿采用一个`# 标题`，随后逐行写大纲，使用两空格缩进一级。下列代码块只展示写法，正式PRD不得带外围代码围栏。

- level 0：`●`，整条模块文字加粗。
- level 1：`○`，仅功能名称加粗；同一行的“对应场景 / 功能描述”不加粗。
- level 2：`■`，系统行为不加粗；字段、状态、设计稿、规则、异常、权限、验收等引导行加粗。
- level 3：`■`，字段、流转、图片、图注、规则、异常、权限、AC等内容不加粗。
- level 4：`■`，枚举选项等下级内容不加粗。

不把一整个功能行加粗，不把系统行为或编号本身额外加粗。DOCX使用真实多级列表，不能把整棵树合并成一个普通段落。

## 业务评审版

以下为结构示意，所有占位内容须替换为已确认陈述或原位“待确认”标注；条件保留小节在无适用内容时整节删除：

```text
# 产品 主题 PRD（业务评审版）
● **模块名称**
  ○ **功能名称：功能名称** / 对应场景：具体场景 / 功能描述：具体能力
    ■ 系统行为陈述，每条只描述一个行为。
    ■ **该功能涉及的字段：**
      ■ 【新增 / 变更 / 删除】字段名 —— 界面栏位变化说明、填写要求与默认值。
        ■ 枚举选项及其业务含义。
    ■ **状态流转：**
      ■ 当前状态 → 目标状态：谁在什么条件下执行什么操作，系统如何联动。
    ■ **设计稿：**
      ■ ![图1：功能说明](<assets\功能设计.png>)
      ■ 图1：功能说明。
    ■ **业务规则与生成逻辑：**
      ■ 计算 / 生成规则：前端仅展示结果字段或统计数据时的后端统计口径、公式或生成逻辑。
```

- 不出现MOD/FR/FLD/TR/BR/EX/RM/AC标识。
- 功能名称下方的系统行为子条目仅陈述本次涉及修改、调整的功能点变化，不写入不涉及变动的其他任务类型/模块“维持原逻辑”等非变动说明。
- 不设置异常场景与边界条件、权限和验收标准小节（这三节仅在开发规格版保留）；必要的使用角色可在对应场景或行为中用自然语言说明。
- “该功能涉及的字段”仅标出本次需求在原有用户操作界面上新增、删除、变更的字段，不罗列未变动的原有相关字段或后端内部字段；若界面无字段增删改，删除该引导行及其子条目。
- 不涉及流程时删除“状态流转”引导行及其全部子条目，不保留空节。
- “业务规则与生成逻辑”非强制输出：只要在设计稿或界面交互上能看出的逻辑均无需展示；仅当后端存在复杂业务逻辑而前端仅展示一个字段或某项数据（例如统计图某项核心指标的统计逻辑、复杂自动计算/编号生成规则）时才保留本小节，无适用内容时整节删除，不留空节。

## 开发规格版

```text
# 产品 主题 PRD（开发规格版）
● **MOD-01 模块：模块名称**
  ○ **FR-01 功能名称：功能名称** / 对应场景：具体场景 / 功能描述：具体能力
    ■ FR-01-1 系统行为陈述，每条逐一编号。
    ■ **该功能涉及的字段：**
      ■ FLD-01 字段名 —— 栏位类型 / 必填条件 / 来源。
        ■ 枚举选项及其含义。
    ■ **状态流转（TR-xxx，仅流程类功能保留）：**
      ■ TR-01 源状态 → 目标状态：触发事件 / 前置条件 / 触发角色 / 副作用（通知、锁定、日志）。
    ■ **设计稿：**
      ■ ![图1：功能说明](<assets\功能设计.png>)
      ■ 图1：功能说明。
    ■ **业务规则与生成逻辑（BR-xxx）：**
      ■ BR-01 校验规则：具体规则（校验层级：双端 / 仅后端，实际选择已确认的一项）。
      ■ BR-02 计算 / 编号生成规则：公式与口径、精度舍入，或编号格式与重置策略（校验层级：双端 / 仅后端）。
    ■ **异常场景与边界条件（EX-xxx）：**
      ■ EX-01 如果发生具体异常，系统会执行具体处理（数据影响：整体回滚 / 部分成功 / 只读保留，实际选择已确认的一项）。
    ■ **权限（RM-xxx）：**
      ■ RM-01 角色：具体角色 —— 本功能操作：具体操作（可用 / 仅查看 / 不可见）；数据范围：已确认范围（如仅本人 / 本部门 / 全部）。
      ■ 越权防护：所有权限在服务端接口层强制校验，前端仅做展示控制。
    ■ **验收标准（AC-xxx）：**
      ■ AC-01 Given 具体前提，When 具体操作，Then 可观察的确定结果与具体数字示例（关联 FR-01-1 / BR-01 / EX-01）。
```

### 编号与追溯

- 追溯链为`MOD/FR → FLD/TR → BR/EX → AC`，RM记录功能级权限。MOD按模块分配，FR按功能分配，行为按`FR-xx-n`逐条编号。
- FLD、TR、BR、EX、RM、AC各自在文档内使用稳定且唯一的编号；同一条规则只声明一次，其余位置显式引用。不同前缀可使用相同数字。
- `TR-xxx`等仅是引导行的编号类型提示，不是实际条目ID；实际条目必须用`TR-01`等唯一编号，禁止把示意占位符原样写入正文。
- 每条AC关联所属FR行为及适用的BR/EX，引用必须能定位到真实条目。没有对应异常时不伪造EX；没有状态流转时不创建TR。
- 规则共用时，在首次声明的功能中写明适用功能范围，其他功能在自己的规则小节引用该规则；业务版用规则名和功能名引用，不暴露编号。
- 更新文档时保留未变更条目的ID，新增条目不复用已删除ID；不为满足模板凭空新增功能或状态。

### 可测试性与不确定项

- 每条BR均注明“校验层级：双端”或“校验层级：仅后端”；未确认写“校验层级：待确认”，不把建议实现当作确认结果。
- 每条EX均注明已确认的数据影响：“整体回滚”“部分成功”或“只读保留”；未确认写“数据影响：待确认”。
- 计算规则必须给出公式、分子分母、排除项和适用的精度/舍入；业务编号写明格式、唯一性和重置策略，均以需求或用户确认为依据。
- AC采用Given-When-Then，包含具体数字示例，不只写“显示正确”。例如已确认改善率口径时：“Given 8个问题中2个可改善、3个难以改善、3个未分类，When 查看可改善率，Then 排除未分类项并显示2÷5=40%（关联实际FR/BR编号）”。
- 不涉及计算的AC也提供可观察的数量或明确输入，例如“两次重复提交仅新增1条记录”；不得据示例反推或发明业务规则。
- 权限必须写角色、操作状态及数据范围；任何一项不明确均写“待确认”，不得预设默认放行；服务端鉴权声明始终保留。
- P0未决时不声称正式定稿；保留同构双版，把待确认事项放到所属功能，不另开问题清单章节。
